## 2026-07-05
**Topics:** chapters as a first-class citizen (Phases 1-2), implemented in an isolated worktree per the Fable-planned/Brian-approved plan (`Launch/plans/chapters-first-class.md`), branch `feature/chapters-first-class`.
**Did:**
- Built `src/shared/chapterSpans.ts` test-first: `deriveChapterSpans(scenes, chapters)` is now the single source of truth for "what's in which chapter." Core semantic: a chapter is a contiguous run of scenes in braid (`timelinePosition`) order, not an independent bucket — contiguity is an application invariant computed at read time, never a DB constraint or a bulk rewrite on load. A chapter's span starts at its first scene's braid position and runs to the next chapter's first scene, which self-heals legacy non-contiguous data without touching the DB.
- **Mid-session plan amendment from Brian:** empty chapters (zero scenes) had to be first-class, since some writers create a chapter with a synopsis before braiding anything into it. Built this into `deriveChapterSpans` from the start (hadn't written the Rails UI yet when the amendment landed) — empty chapters are positioned among populated ones by `chapters.order`, interpolated relative to whichever populated chapters are around them. 21 unit tests cover: no chapters, empty-chapters-array, contiguous data, legacy non-contiguous data (self-heals), unbraided scenes excluded, all-unassigned, and all four empty-chapter placements the amendment named (between populated, at start, at end, all-empty-with-unassigned-scenes-present).
- Also added `reconcileChaptersAfterBraidChange` (the Phase 2 invariant enforcer — computes which scenes' chapter assignment needs to change after a braid move, only for the affected scenes), `computeInsertChapterAssignments`, and `computeDeleteChapterAssignments` (delete-merges-into-preceding logic) — all pure, all unit tested.
- **Phase 1 (Rails):** Rails is now the full chapter management surface. Create via "+ Chapter" affordances between chapter groups and at the top/bottom of the braid (creates an empty chapter positioned by `order`, no scene grabbed), plus the toolbar "+ New Chapter" button (now shown for Rails too — previously the toolbar item only worked in List view) which always appends an empty chapter at the end. Rename is click-to-edit inline on the chapter title, same commit-on-blur/Enter, Escape-cancels pattern as the Outline view's scene titles. Delete now merges the chapter's scenes into the *preceding* chapter's span (or "No chapter" if none precedes) with a confirm dialog stating exactly that — previously delete just orphaned scenes via a DB foreign-key `SET NULL`, silently. Empty chapters render as a header + an explicit drop zone; dropping a scene there routes through the existing `onDropOnTimeline` at that braid position, and Phase 2's reconciliation naturally picks up the new chapter as soon as a scene lands in it. Chapters are no longer independently drag-reorderable in Rails (order is derived from span position; the `order` column is kept in sync as bookkeeping via `reorderChapters`, not user-draggable).
- **Phase 2 (assignment automation):** found and routed all 7 real braid-mutation call sites in `App.tsx` (`handleDropOnTimeline`, `handleDropOnInbox`, `handleBraidedReorder`, `handleBraidedMoveToInbox`, `handleBraidedMoveFromInbox`, `handleInsertSceneAtPosition`, `handleReorderScenesFromTable`) through one shared `reconcileChaptersForScenes` helper, which is a no-op with zero overhead when a project has no chapters at all (the "strictly optional" requirement).
- **Risk checks turned out to be moot, verified against actual code, not assumed:** the plan flagged a "sibling risk" to the known plot-points bulk-save landmine — a bulk `saveTimeline` payload silently wiping `chapterId`. Traced it and found `applySaveTimeline` is already a confirmed no-op (Phase 4g retired it; the `BRAIDR_SAVE_TIMELINE` IPC handler itself no longer exists in `braidrIpc.ts`/`main.ts`, and nothing in the renderer even calls the preload binding anymore) — all scene writes now go through named per-field mutations. Added a regression test locking this in anyway (`save-timeline-preserves-chapters.test.ts`), since the plan explicitly asked for one and it's cheap insurance against a future re-introduction. Also verified branch snapshot/restore already round-trips chapters correctly (`chapters` and `scenes.chapter_id` are both in `BRANCHED_TABLES`, and the swap is a generic column-agnostic JSON round-trip) — added a dedicated test (`branchStorage.test.ts`) proving it, rather than just trusting the code read.
- **Real gap found in the existing code, not fixed this pass (flagged for Brian):** `BraidedListView` (the List sub-mode, studio-build-only) has its own, separate "chapter buckets" implementation — cross-container drag-and-drop that assigns any scene to any chapter independent of braid position, plus its own drag-to-reorder-chapters UI. This is exactly the "independent buckets" model the new core semantic explicitly rejects, and it still exists untouched. `PovOutlineView` and `TableView`/`OutlineView` also still read `scene.chapterId` directly (bucket-style, non-contiguous-prone) rather than through `deriveChapterSpans`. Reconciling these is Phase 3 work per the plan; documented as a known inconsistency in `docs/features.md` and `STATUS.md` rather than silently left for someone to discover later.
